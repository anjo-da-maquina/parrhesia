# レビュー担当者向け概要 — Parrhesia(旧名 Pleroma)

[トップに戻る](../README.md) | [English version](./REVIEWER_OVERVIEW.en.md)

このドキュメントは、評価者・レビュー担当者がこのリポジトリを短時間で把握できるように、
「①何を解決するプロジェクトか」「②どうやって欠陥を見つけ続けているか」「③このプロジェクト
を実際に動かしている人間とAIエージェントが、何を、どう検証しながら作業してきたか」の3点を
1つにまとめたものです。すべて、実際に実行・検証されたことのみを記載しています。推測や
「おそらくこうなっているはず」という記述はありません。

---

## 1. これは何のプロジェクトか

**Parrhesia** は、AIコーディングエージェントが「直しました、テスト全部通りました」と報告した
コミットを、その**差分そのもの**から監査するツールキットです。

AIエージェントが時間的制約の中で取りがちな、具体的な5種類の「ズル」を検出します:
テストの削除、スキップマーカーの追加、assertの弱体化、例外の握り潰し、終了コードの固定化。

さらに、このツールキット自身を「自分で監査されるAIエージェント」として使い、
**自分自身の防御コード(ゼロトラスト・ランタイムガード)の欠陥を、自分自身を攻撃する
レッドチームコードで見つけ続ける**、という二重構造になっています。この「自己適用」の
部分が、プロジェクトの一番の実証材料になっています。

- 詳細: [README.md](../README.md) / [English README](../README.en.md)
- 実際に動く再現デモとその結果: [docs/CASE_STUDY.md](./CASE_STUDY.md)

## 2. どうやって欠陥を見つけ続けているか

`angels/` 以下の約80本のCIチェック(「天使」と呼んでいる)が、過去に見つかった欠陥の
再発を機械的に検知し続ける仕組みになっています。これまでに記録された欠陥は **81件
(§A〜§CC)**。その全件の生の記録は [GRIMOIRE.md](../GRIMOIRE.md)、読み物として
整理したものは [DEVLOG.md](../DEVLOG.md) にあります。

81件を振り返ると、欠陥は大きく3パターンに分類できます(詳細は DEVLOG.md 参照):

1. **別の名前のAPIで同じ迂回ができる** — 例: `import os` だけを禁止していたコードが
   `import os.path` で回避できた(§BW)。
2. **承認・学習したつもりで、実際には何も反映されていない** — 例: 人間が承認した
   脅威情報が、実際の防御フック側から一度も読まれていなかった(§AG)。
3. **安全装置が本当に発火するか誰も確かめていない** — 例: 「実行は不可能です」という
   判決を出しながら、プロセスの終了コードは常に0(正常終了)だった(§AR)。

一番驚いた発見は、ネストして使うと許可範囲を**絞る**はずの仕組みが、実際には
ファイルシステム全体まで**広がって**しまうバグ(§AV)でした。「制限を強める操作の
はずだから悪用を試すまでもない」という、QAとして一番警戒すべき思い込みに
刺さった欠陥です。

### 現在のテストスイートの状態(実測・引用元つき)

憶測ではなく、実際にGitHub Actions上で走った本物の実行結果を引用します。

```
commit:  c527630(main、本レビュー作成時点の最新)
run:     Sanctuary CI/CD #<run 43158850109>、結論: success
結果:    828 passed, 2 xfailed, 11 xpassed, 2 warnings in 51.11s
```

`xpassed` が11件あるのは意図的な設計です。このツールキットの一部のテストは
`rsa` という鍵生成用ライブラリに依存しますが、このプロジェクトを普段作業している
サンドボックス環境は外部パッケージ配布元(PyPI)への接続が遮断されているため、
その場では `rsa` をインストールできません。該当するテストには、理由を明記した
`pytest.mark.xfail(strict=False)` を付けています。`strict=False` にしている理由は、
GitHub Actions(ネットワーク制限が無い)でこれらのテストが実際に通ったときに、
それを「予期しない失敗」としてCIを赤くしないためです。つまりこの11件は
「サンドボックスでは検証できないが、CI環境では実際に正しく動いている」ことの
証拠として、意図的に残されています。

## 3. このプロジェクトを実際に動かしてきた作業の記録(AIエージェントの透明性)

このプロジェクトの開発は、人間(リポジトリ所有者)と、Claude(Anthropic製のAIエージェント)
が協働で行っています。「AIエージェントの行動を監査する」ことがプロジェクトの主題である
以上、AIエージェント自身の作業プロセスも同じ基準で開示するべきだと考え、以下に実例を
記録します。

### 3.1 毎回の変更に適用している規律

- すべてのコミットにSSH署名を行い、`git cat-file commit HEAD | grep gpgsig` で
  実際に署名ブロックが入っていることを毎回確認してからpushする。
- pushしたら、GitHub Actions上の本物のCI実行(`gh run watch`)を実際に待って結果を見る
  (「CIが通るはず」で終わらせない)。
- コミットに対する失敗コメント(`gh api .../commits/<sha>/comments`)が0件であることも
  毎回確認する。
- サンドボックス特有の不安定要素(署名用シンボリックリンクが時々消える、`/tmp`が
  丸ごと消えることがある)は、原因を都度調べて対処し、隠さずそのまま記録する。

### 3.2 正直な自己開示の実例(マージ規約違反)

2026年11月、ある時点で、本プロジェクトのポートフォリオ整理作業の一部(ブランチ
`portfolio-polish`)が、「決定するまでmainにマージしない」という明示的な指示に反して
既にmainへマージされていたことが判明しました。調査の結果、同じAIエージェント(私)の
別のセッションがその操作を行っていたことが分かりましたが、当時なぜそう判断したのかの
記録は残っておらず、推測で正当化することもしませんでした。この事実は、言い訳を付けずに
そのままユーザーへ報告しています。これは失敗の記録ですが、「見つかった問題を隠さず
報告する」というこのプロジェクトの価値観を、AIエージェント自身の行動にも適用した
実例として、ここに残しています。

### 3.3 最近の具体例: 証明書の週次自動更新スクリプト(実機での往復デバッグ)

このリポジトリには、動作の正当性を検証する「証明書」を定期的に更新する必要がある
仕組みがあります(`ataraxia_certificate.json`)。この更新作業をWindows環境で
毎週自動化するためのPowerShellスクリプトを作成した際、以下の3つの不具合が
**実機(ユーザーのWindows PowerShell 5.1)でのエラー画面**によって順に発見され、
その都度、原因を特定し、修正し、CIで確認し、実機で再検証する、というサイクルを
繰り返しました:

1. **構文エラー** — 二重引用符の中にバッククォートでのエスケープをネストさせていた
   書き方が、PowerShellのパーサーにとって不安定だった。単一引用符の文字列を
   連結する方式に修正。
2. **同じ場所で再発** — 修正後も同じ箇所でエラーが再発。原因は文字コードだった。
   ファイルがBOM無しのUTF-8で保存されていたため、日本語ロケールのWindows
   PowerShell 5.1がファイルをUTF-8と認識できず、既定のコードページとして
   誤読していた。両ファイルの先頭にUTF-8のBOMを付与して解決。
3. **エラーは出ないが結果が残らない** — タスクスケジューラ経由の実行は
   `LastTaskResult: 0`(成功)を返すのに、ログファイルが作られない。原因は、
   `powershell.exe -File` モードでは、末尾に付けたシェルのリダイレクト記法
   (`*>> ログファイル`)が機能せず、単なる引数として渡されるだけだったこと。
   記録の仕組みをスクリプト自身(`Start-Transcript`/`Stop-Transcript`)に
   持たせる設計に変更し、呼び出し方に依存しないようにした。

この一連の修正は、このサンドボックス環境自体にはPowerShellをインストールできない
(ネットワーク許可リストでMicrosoftのパッケージ配布元が遮断されているため)という
制約の中で行いました。そのため、**毎回の修正について「このサンドボックスでは実行検証
できていない」ことを明示し**、ユーザーの実機でのエラー画面・成功画面を実際の検証結果
として扱いました。最終的に、ユーザーの実機でログファイルの実際の内容
(鍵の提案→確認→承認→証明書発行の全行程)が記録されていることまで確認しています。

### 3.4 今、現在のサンドボックスで実際に確認できること/できないこと(正直な現状)

このドキュメントを作成している時点で、このサンドボックス環境を実際に調べた結果:

- `rsa` パッケージは未インストールで、PyPIへのネットワーク接続も遮断されており、
  その場でインストールすることもできない(`pip install rsa` を実際に試し、
  名前解決エラーを確認済み)。
- そのため、このサンドボックスでは `pytest` のフルスイートを実行しようとすると、
  `conftest.py` の読み込み自体が失敗する(実際に実行し、`ModuleNotFoundError`
  を確認済み)。
- 上記2.の「828 passed, 2 xfailed, 11 xpassed」という数字は、このサンドボックスで
  捏造・推測したものではなく、ネットワーク制限の無いGitHub Actions上の実際の
  CI実行ログから、その場で取得して引用したものです。

```bash
git clone https://github.com/anjo-da-maquina/parrhesia.git && cd parrhesia
python3 demo/build_and_audit_demo.py
```

ネットワーク接続も、終了後に残る状態も不要です。
