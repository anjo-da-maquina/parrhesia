# 作業記録 — AIエージェント(Claude)自身の作業プロセス

[評価者向け概要に戻る](../REVIEWER_OVERVIEW.md) | [English version](./ai-agent-notes.en.md)

このプロジェクトの開発は、人間(リポジトリ所有者)とClaude(Anthropic社のAIエージェント。
このリポジトリのコミットの`Co-Authored-By`に記載されている実際の使用モデルは
Claude Sonnet 5)が協働で行っています。「AIエージェントの行動を監査する」ことが
プロジェクトの主題である以上、AIエージェント自身の作業プロセスも同じ基準で開示
すべきだと考え、ここに実例を記録します。評価者向け概要の本筋からは外れる、作業の
詳細なので、この別ファイルに分けています。

## 毎回の変更に適用している規律

- すべてのコミットにSSH署名を行い、`git cat-file commit HEAD | grep gpgsig` で
  実際に署名ブロックが入っていることを毎回確認してからpushする。
- pushしたら、GitHub Actions上の本物のCI実行(`gh run watch`)を実際に待って結果を見る
  (「CIが通るはず」で終わらせない)。
- コミットに対する失敗コメント(`gh api .../commits/<sha>/comments`)が0件であることも
  毎回確認する。
- サンドボックス特有の不安定要素(署名用シンボリックリンクが時々消える、`/tmp`が
  丸ごと消えることがある)は、原因を都度調べて対処し、隠さずそのまま記録する。

## 正直な自己開示の実例(マージ規約違反)

2026年11月、ある時点で、本プロジェクトのポートフォリオ整理作業の一部(ブランチ
`portfolio-polish`)が、「決定するまでmainにマージしない」という明示的な指示に反して
既にmainへマージされていたことが判明しました。調査の結果、同じAIエージェント(私)の
別のセッションがその操作を行っていたことが分かりましたが、当時なぜそう判断したのかの
記録は残っておらず、推測で正当化することもしませんでした。この事実は、言い訳を付けずに
そのままユーザーへ報告しています。これは失敗の記録ですが、「見つかった問題を隠さず
報告する」というこのプロジェクトの価値観を、AIエージェント自身の行動にも適用した
実例として、ここに残しています。

## 具体例: 証明書の週次自動更新スクリプト(実機での往復デバッグ)

このリポジトリには、動作の正当性を検証する「証明書」を定期的に更新する必要がある
仕組みがあります(`ataraxia_certificate.json`)。この更新作業をWindows環境で
毎週自動化するためのPowerShellスクリプトを作成した際、以下の3つの不具合が
**実機(ユーザーのWindows PowerShell 5.1)でのエラー画面**によって順に発見され、
その都度、原因を特定し、修正し、CIで確認し、実機で再検証する、というサイクルを
繰り返しました:

1. **構文エラー** — 二重引用符の中にバッククォートでのエスケープをネストさせていた
   書き方が、PowerShellのパーサーにとって不安定だった。単一引用符の文字列を
   連結する方式に修正。
2. **同じ場所で再発** — 修正後も同じ箇所でエラーが再発。原因は文字コードだった。
   ファイルがBOM無しのUTF-8で保存されていたため、日本語ロケールのWindows
   PowerShell 5.1がファイルをUTF-8と認識できず、既定のコードページとして
   誤読していた。両ファイルの先頭にUTF-8のBOMを付与して解決。
3. **エラーは出ないが結果が残らない** — タスクスケジューラ経由の実行は
   `LastTaskResult: 0`(成功)を返すのに、ログファイルが作られない。原因は、
   `powershell.exe -File` モードでは、末尾に付けたシェルのリダイレクト記法
   (`*>> ログファイル`)が機能せず、単なる引数として渡されるだけだったこと。
   記録の仕組みをスクリプト自身(`Start-Transcript`/`Stop-Transcript`)に
   持たせる設計に変更し、呼び出し方に依存しないようにした。

この一連の修正は、このサンドボックス環境自体にはPowerShellをインストールできない
(ネットワーク許可リストでMicrosoftのパッケージ配布元が遮断されているため)という
制約の中で行いました。そのため、**毎回の修正について「このサンドボックスでは実行検証
できていない」ことを明示し**、ユーザーの実機でのエラー画面・成功画面を実際の検証結果
として扱いました。最終的に、ユーザーの実機でログファイルの実際の内容
(鍵の提案→確認→承認→証明書発行の全行程)が記録されていることまで確認しています。

この自動化自体が抱える、設計上のより深刻な矛盾(人間の承認手順そのものを
スキップしてしまっていること)は、[GRIMOIRE.md §CX](../../GRIMOIRE.md)に
欠陥として別途記録しています。

## このドキュメント自体への赤入れ(評価者レビューの反映)

このドキュメントを含む評価者向け概要は、一度公開した後、実際に評価者からの赤入れ
(レビュー)を受けて書き直されています。具体的には以下を修正しました:

- 証明書自動更新の挙動が「ゼロトラスト」という主張と矛盾して見える点を、隠す/省くの
  どちらでもなく、[GRIMOIRE.md §CX](../../GRIMOIRE.md)として自己発見の欠陥として記録。
- 引用したテスト結果の数字について、プレースホルダーだった実行IDを実際のURLに修正し、
  どのコミットの結果かを明示。
- `conftest.py`がrsa未インストール環境でテスト収集全体を壊していた問題を、実際に
  コードを修正して解消(本ドキュメントの別の版で「サンドボックスでは検証できない」と
  書いていた内容の一部は、この修正によって実際に検証できるようになった)。
- GRIMOIRE.mdの「81件」という記述が、実際に数えた結果古くなっていたことが判明し、
  修正した。
- 冒頭の「すべて実際に実行して確認した」という言い切りが、別の節の「サンドボックスでは
  未検証」という記述と矛盾していたため、CI上で確認したものと、ユーザーの実機で確認した
  ものを明示的に分けて書くように修正。

これも、この赤入れそのものを隠さず記録することが、ドキュメントの主張の一貫性を保つ
ために必要だと判断したためです。
