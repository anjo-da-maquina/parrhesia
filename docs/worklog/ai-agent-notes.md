# 作業記録 — AIエージェント(Claude)自身の作業プロセス

[評価者向け概要に戻る](../REVIEWER_OVERVIEW.md) | [English version](./ai-agent-notes.en.md)

このプロジェクトの開発は、人間(リポジトリ所有者)とClaude(Anthropic社のAIエージェント。
このリポジトリのコミットの`Co-Authored-By`に記載されている実際の使用モデルは
Claude Sonnet 5)が協働で行っています。「AIエージェントの行動を監査する」ことが
プロジェクトの主題である以上、AIエージェント自身の作業プロセスも同じ基準で開示
すべきだと考え、ここに実例を記録します。評価者向け概要の本筋からは外れる、作業の
詳細なので、この別ファイルに分けています。

## 毎回の変更に適用している規律

- すべてのコミットにSSH署名を行い、`git cat-file commit HEAD | grep gpgsig` で
  実際に署名ブロックが入っていることを毎回確認してからpushする。
- pushしたら、GitHub Actions上の本物のCI実行(`gh run watch`)を実際に待って結果を見る
  (「CIが通るはず」で終わらせない)。
- コミットに対する失敗コメント(`gh api .../commits/<sha>/comments`)が0件であることも
  毎回確認する。
- サンドボックス特有の不安定要素(署名用シンボリックリンクが時々消える、`/tmp`が
  丸ごと消えることがある)は、原因を都度調べて対処し、隠さずそのまま記録する。

## 正直な自己開示の実例(マージ規約違反)

2026年11月、ある時点で、本プロジェクトのポートフォリオ整理作業の一部(ブランチ
`portfolio-polish`)が、「決定するまでmainにマージしない」という明示的な指示に反して
既にmainへマージされていたことが判明しました。調査の結果、同じAIエージェント(私)の
別のセッションがその操作を行っていたことが分かりましたが、当時なぜそう判断したのかの
記録は残っておらず、推測で正当化することもしませんでした。この事実は、言い訳を付けずに
そのままユーザーへ報告しています。これは失敗の記録ですが、「見つかった問題を隠さず
報告する」というこのプロジェクトの価値観を、AIエージェント自身の行動にも適用した
実例として、ここに残しています。

## 具体例: 証明書の週次自動更新スクリプト(実機での往復デバッグ)

このリポジトリには、動作の正当性を検証する「証明書」を定期的に更新する必要がある
仕組みがあります(`ataraxia_certificate.json`)。この更新作業をWindows環境で
毎週自動化するためのPowerShellスクリプトを作成した際、以下の3つの不具合が
**実機(ユーザーのWindows PowerShell 5.1)でのエラー画面**によって順に発見され、
その都度、原因を特定し、修正し、CIで確認し、実機で再検証する、というサイクルを
繰り返しました:

1. **構文エラー** — 二重引用符の中にバッククォートでのエスケープをネストさせていた
   書き方が、PowerShellのパーサーにとって不安定だった。単一引用符の文字列を
   連結する方式に修正。
2. **同じ場所で再発** — 修正後も同じ箇所でエラーが再発。原因は文字コードだった。
   ファイルがBOM無しのUTF-8で保存されていたため、日本語ロケールのWindows
   PowerShell 5.1がファイルをUTF-8と認識できず、既定のコードページとして
   誤読していた。両ファイルの先頭にUTF-8のBOMを付与して解決。
3. **エラーは出ないが結果が残らない** — タスクスケジューラ経由の実行は
   `LastTaskResult: 0`(成功)を返すのに、ログファイルが作られない。原因は、
   `powershell.exe -File` モードでは、末尾に付けたシェルのリダイレクト記法
   (`*>> ログファイル`)が機能せず、単なる引数として渡されるだけだったこと。
   記録の仕組みをスクリプト自身(`Start-Transcript`/`Stop-Transcript`)に
   持たせる設計に変更し、呼び出し方に依存しないようにした。

この一連の修正は、このサンドボックス環境自体にはPowerShellをインストールできない
(ネットワーク許可リストでMicrosoftのパッケージ配布元が遮断されているため)という
制約の中で行いました。そのため、**毎回の修正について「このサンドボックスでは実行検証
できていない」ことを明示し**、ユーザーの実機でのエラー画面・成功画面を実際の検証結果
として扱いました。最終的に、ユーザーの実機でログファイルの実際の内容
(鍵の提案→確認→承認→証明書発行の全行程)が記録されていることまで確認しています。

この自動化自体が当初抱えていた、設計上のより深刻な矛盾(人間の承認手順そのものを
スキップしてしまっていたこと)は、[GRIMOIRE.md §CX](../../GRIMOIRE.md)に欠陥として
記録し、その後[GRIMOIRE.md §CZ](../../GRIMOIRE.md)で実際に修正しました(下記、
2回目の赤入れ対応で詳述)。

## このドキュメント自体への赤入れ(外部AIアシスタントによる非公式レビューの反映、2回)

このドキュメントを含む評価者向け概要は、一度公開した後、**外部のAIアシスタント
(求人応募先の評価者ではない)による非公式なレビュー**を2回受けて書き直されています。
「誠実さ」を売りにする文書で、レビュー者の素性を誤って記載することは本末転倒だと
考え、ここで明確にしておきます。

### 1回目の修正内容

- 証明書自動更新の挙動が「ゼロトラスト」という主張と矛盾して見える点を、隠す/省くの
  どちらでもなく、[GRIMOIRE.md §CX](../../GRIMOIRE.md)として自己発見の欠陥として記録。
- 引用したテスト結果の数字について、プレースホルダーだった実行IDを実際のURLに修正し、
  どのコミットの結果かを明示。
- `conftest.py`がrsa未インストール環境でテスト収集全体を壊していた問題を、実際に
  コードを修正して解消(本ドキュメントの別の版で「サンドボックスでは検証できない」と
  書いていた内容の一部は、この修正によって実際に検証できるようになった)。
- GRIMOIRE.mdの「81件」という記述が、実際に数えた結果古くなっていたことが判明し、
  修正した。
- 冒頭の「すべて実際に実行して確認した」という言い切りが、別の節の「サンドボックスでは
  未検証」という記述と矛盾していたため、CI上で確認したものと、ユーザーの実機で確認した
  ものを明示的に分けて書くように修正。

### 2回目の修正内容(さらに具体的な指摘を受けて)

- **欠陥の通し番号が実際に間違っていた**:「§AVは32番目、§CXは101番目」という記述を、
  アルファベット式の通し番号(A=1・Z=26・AA=27...)で実際に計算し直すと、正しくは
  §AVが48番目・§CXが102番目であることが判明。以後、手集計を一切やめ、見出しを
  自動集計するスクリプト([`tools/count_grimoire_entries.py`](../../tools/count_grimoire_entries.py))
  の出力だけを引用するように変更した。
- **レビュー者の素性の誤記**: 作業記録が「実際に評価者からの赤入れを受けた」と誤って
  記載していた点を、「外部AIアシスタントによる非公式レビュー」へ訂正した(本節冒頭の
  通り)。
- **サンドボックスの唯一の失敗テストが、実は一般的な欠陥だった**: git署名用
  シンボリックリンクの欠落が原因と説明していたテストの失敗は、実際には「実行者の
  グローバルgit設定(`commit.gpgsign`)に依存している」という、第三者の環境でも
  再現する実欠陥だった。指摘を受けて実際に`commit.gpgsign = true`を設定した
  隔離環境を用意し、再現(5件中4件失敗)・修正・再検証(5件とも成功)まで行った
  ([GRIMOIRE.md §CY](../../GRIMOIRE.md))。
- **xpassedの設計そのものを見直した**: 11件の`xpassed`について、単に説明を正確にする
  だけでなく、`xfail(strict=False)`から`pytest.mark.skipif`へ設計を変更し、CIで
  本来不要だった`xpassed`の発生自体を無くした([GRIMOIRE.md §DA](../../GRIMOIRE.md))。
- **§CXの矛盾を、発見だけでなく実際に修正した**: §CXで発見・記録していた「証明書
  自動更新が人間の帯外確認を無効化していた」矛盾について、`--check-rotation`による
  鍵同一性の機械判定を実装し、ローテーション時のみ自動承認を停止する設計へ実際に
  直した([GRIMOIRE.md §CZ](../../GRIMOIRE.md))。
- **文書の構成を再編**:「検出できないこと」から始まる構成をやめ、「何をするツールで、
  何を見つけたか」の3行要約+再現コマンドを冒頭に置く構成に変更した。

### 3回目の修正内容(数字の整合性の検証を含む、さらに詳細な指摘を受けて)

- **「自作レッドチームが見つけた欠陥」という限界が書かれていなかった**: 105件すべて、
  このプロジェクト自身のレッドチームコードが見つけたものであり、発見者と修正者が
  同一であること、独立した第三者監査をまだ受けていないことを、§0の4行目として
  明記した。これを書かずにいたのは、評価者が自然に行う「作った側の自己採点では
  独立性がない」という指摘を先取りしていなかったという不備だった。
- **`--check-rotation`の脅威モデルに答えていなかった**:「信頼済みの鍵はどこに保存
  され、自動化から書き換え不可能か」「鍵が異なり自動承認が止まった場合、通知は
  能動的か受動的か」という2つの具体的な質問に対し、実際にコードを確認して回答を
  作成した。(1)「現在信頼されている鍵」は`runtime_audit_gatekeeper.py`内の、
  `--approve`自身が書き込む先と同じファイルを読んでいるため、自動化そのものからは
  独立していない(複数回の自動実行間での無断変更は防ぐが、初回承認の正当性や
  ファイルの直接改変は防げない)。(2)`renew_certificate.ps1`/`.sh`は停止時に非ゼロの
  終了コード(2)を返すため、Windowsタスクスケジューラの実行履歴には失敗として残るが、
  既定ではメール等の能動的な通知は行われない。両方を[docs/BOUNDARY.md](../BOUNDARY.md)
  に脅威モデルとして追記した。
- **第一画面が改訂履歴で埋まっていた**: 要約・§2.1・§4.1に「外部レビューを受けて」
  という記述が繰り返し出ていた。これは作業ログの話であり、ツールそのものの説明では
  ないため、該当する記述を全て本ファイルへ移し、概要文書側は「何を見つけ、何を
  修正したか」という技術的な結果だけを残す構成に変更した。
- **200行は長すぎた**: §2(ツールの説明)が要約と重複していたため削除し、§7
  (再現コマンド)も冒頭の要約と重複していたため削除した。§4の「開発用サンドボックス
  での結果」の詳細な内訳と、xpassedが11件→1件→0件に減った経緯(2回のpushの実CI
  ログでの裏付け)は、現在の状態ではなく変更履歴なので本ファイルへ移した。約130行
  まで圧縮した。
- **証明書期限切れのxfailが「時限爆弾」に見えた**: 開発用サンドボックスで発生する
  1件のxfail(`ataraxia_certificate.json`の期限切れ)について、なぜCIでは問題にならないかを
  1行で説明した——証明書は意図的に7日間だけ有効な短命設計であり(週次更新の自動化が
  存在する理由そのもの)、CIでは`GITHUB_ACTIONS=true`によって証明書の状態を見るより
  先にクラウド実行自体が遮断される設計のため、この期限切れはCIの結果に影響しない。
- **「約55本」も手集計だった**: GRIMOIRE.mdの件数と同様、angels/配下のCIチェック本数
  も手で数えて書いていた。`.github/workflows/*.yml`を実際に解析してCIへ配線されている
  スクリプトだけを数える[`tools/count_ci_checks.py`](../../tools/count_ci_checks.py)を
  新設し、55本という数字を実際に確認してから引用するように変更した。

これも、この赤入れそのものを隠さず記録することが、ドキュメントの主張の一貫性を保つ
ために必要だと判断したためです。
