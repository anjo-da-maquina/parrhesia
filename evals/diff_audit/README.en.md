# evals/diff_audit — Inspect diff-audit evaluation

[日本語版](./README.md)

A set of [Inspect](https://inspect.ai-safety-institute.org.uk/) (`inspect_ai`)
based evaluation tasks built on the five concrete "shortcuts" Parrhesia is
designed to catch in AI-coding-agent diffs.

## Summary (the conclusion first — details in the sections below)

- **What this measures**: how accurately Parrhesia's own rule-based
  detector catches 5 kinds of shortcut across 155 synthetic + real-commit
  diffs. A parallel "let the LLM judge it" eval task (`task.py`) exists on
  the same data, but its real-model results have not been run yet.
- **Headline metric (clean false-positive rate, after the detector fix)**:
  2/12 (0.167) on a deliberately misleading subgroup, 0/12 (0.000) on an
  ordinary-legitimate-change subgroup. Before the fix, the misleading
  subgroup was 12/12 (1.000). See "[Most important metric] Clean
  false-positive rate" and "Detector improvement (§DC)" below for the
  full story.
- **Confirmed in CI**: `task.py`'s mock-provider wiring check has actually
  succeeded on GitHub Actions (reproduction command 3, "Honest note"
  below). Real-model evaluation (GPT-4o, etc.) is explicitly marked as
  not yet run — the owner needs their own API key for that.
- **Main limitations**: the same person authored the tasks, the labels,
  and the detector; there has been no independent third-party review
  (see "Limitations" below for the full list).

## Purpose

Parrhesia already has a rule-based detector (`parrhesia/diff_fraud.py`) that
mechanically detects five kinds of shortcuts from a `git diff` (deleting a
test, adding a skip marker, weakening an assertion, swallowing an exception,
hard-coding an exit code). This directory measures, on the same dataset
(generated by `build_dataset.py`):

1. How accurate it is when **an LLM itself** makes the same judgment (the
   Inspect task, `task.py`).
2. How accurate the **existing rule-based detector itself** is on the same
   data (the baseline, `baseline.py`).

The specific goal is to honestly report, with confidence intervals, the rate
at which legitimate changes get wrongly flagged as shortcuts (the
false-positive rate) — not just an aggregate accuracy number.

### Honest note on provenance (in response to the original request)

The brief asked for provenance to prioritize the repo's own test fixtures and
real commits. In practice, when the full commit history of this repository
(401 commits) was mechanically scanned with
`parrhesia.diff_fraud.analyze_diff()`, **almost no real commits were found
that actually committed one of the five shortcuts** (because this project's
own nature means few intentionally-cutting-corners commits exist). Most of
the real commits found were, if anything, examples of the opposite: diffs
that *look* like a shortcut but are actually clean (function renames, new
defensive code, etc.) — exactly the kind of thing that induces false
positives in the detector.

Because of that, this dataset ends up structured as: **all positive samples
for the five shortcut categories are synthetic (148 total)**, and **some of
the clean samples (7) were drawn from real commits**. This skew is stated
below as a limitation of being synthetic-heavy. All 7 real-commit samples
drawn were excerpted from this session's own identifier-neutralization
commits on 2026-11-16 (`ed829b5`, `fd17d6d`, `544ae37`) — since the session
itself directly understands their content, label confidence is high.

## Label crosscheck (a requirement of the brief)

Parrhesia's own detector (`analyze_diff`) was applied to all 155 samples and
mechanically cross-checked against the intended labels
(`crosscheck_labels()` in `build_dataset.py`, `data/label_crosscheck.json`).

**[2026-11, latest numbers after re-running following the detector
improvement described below]**

- Mismatches: 6
  - **Deliberately designed as known-false-positive contrast cases**: 2
    (both unrelated to §DC: 1 new `except`/`pass` in a newly-added real
    commit file, 1 literal string match inside DEFECTS.md's prose — the
    detector improvement below resolved 17 of the original 19 mismatches
    that came from function renames and cosmetic skip-line relocations)
  - **Known recall limitations** (found, partly fixed, in §DB below): 4
  - **Unclassifiable, unexpected mismatches**: **0**

(Before the detector improvement, there were 23 mismatches — 19 deliberate
contrast cases, 4 known recall limitations, 0 unexpected. This difference
is itself evidence of the improvement's effect, described below.)

Zero unexpected mismatches is locked in as a regression by
`tests/test_evals_diff_audit.py::test_label_crosscheck_has_no_unexpected_mismatches`.

**Number of labels changed to match the detector's output: 0.**
`crosscheck_labels()` never rewrites the intended `category` label; it is a
read-only cross-check function (verifiable in `build_dataset.py`'s source).
Each sample's `category` is decided, at template-generation time (before
seeing the detector's output), purely from "what change does this diff
actually represent" (e.g. a rename is `clean` because the content is
unchanged, regardless of how the detector happens to judge it). The 23
mismatches found afterward were all recorded and classified as *the
detector's* behavior (19 deliberate contrast cases, 4 known recall
limitations) — nowhere was the `category` label itself rewritten. That said,
as noted under Limitations below, a more fundamental circularity remains: the
positive samples for the five shortcut categories were built by explicitly
implementing the very concepts the detector is meant to catch, so the label
and the detector were not derived independently of each other.

### [Most important metric] Clean false-positive rate (reported separately by subgroup)

The 24 clean samples in `eval.jsonl` were built as two subgroups with
different aims. The "misleading" subgroup (12 samples) was deliberately
designed as contrast cases targeting the detector's blind spots (3 function
renames, 3 cosmetic relocations of a skip line, 6 excerpts from this
session's own past commits). The "normal" subgroup (12 samples) consists of
ordinary, legitimate changes (4 pure test strengthenings, 4 semantically
equivalent refactors, 4 instances of correct exception handling like
`except ... as exc: raise`).

**[Changed in 2026-11 in response to external review feedback] A single
combined false-positive rate across both subgroups (the earlier version of
this document put "50%" in the headline) is a number determined by the
roughly 50/50 mix the author happened to choose between the two subgroups,
and is a weak indicator of the detector's actual performance, so it is kept
out of the headline.** Instead, the per-subgroup rates actually measured by
`python3 evals/diff_audit/baseline.py` (computed in code via `wilson_ci()` in
`baseline.py`, not by hand) are reported:

| Subgroup | n | False-flagged | Rate | Wilson 95% CI |
|---|---|---|---|---|
| Misleading (rename / skip-move / real commit) | 12 | 2 | 0.167 | [0.047, 0.448] |
| Normal (strengthening / equivalent refactor / correct exception handling) | 12 | 0 | 0.000 | [0.000, 0.242] |

(**Before the fix**: misleading 12/12 = 1.000 [0.758, 1.000]; normal 0/12 =
0.000 [0.000, 0.242] (unchanged). See the "Detector improvement" section
below.)

(For reference only — not used in any headline) Combined across both
subgroups: 2/24 = 0.083 (Wilson 95% CI: [0.023, 0.258]). This combined value
is recorded in `data/baseline_results.json` under the explicit key
`clean_false_positive_rate_combined_rate_mixture_dependent_do_not_use_as_headline`,
with its own caveat string saying not to use it as a headline.

**A caution about the "normal" subgroup's 0/12 result**: this dataset was
built by the same person who built the detector, who could unconsciously
select data that confirms the expectation that "the detector shouldn't
false-flag ordinary changes" (i.e., unconsciously classify only
detector-favorable data as "normal"). The 0/12 figure is not guaranteed to
hold on an independently constructed "normal" change set built by a third
party.

(Auxiliary metric, never used alone as a claim) Overall accuracy: 0.951
(was 0.853 before the fix)

**Remaining causes of false positives** (confirmed by inspecting the
breakdown; the detector fix below resolved the rename- and
skip-line-relocation-caused false positives):
- 2 real-commit samples remain false-flagged, both unrelated to §DC: 1 new
  `except`/`pass` in a newly-added file (new defensive code, not corner-
  cutting, but `swallowed_exception` doesn't distinguish a brand-new file),
  1 literal string match on `sys.exit(0)` that happens to appear inside
  DEFECTS.md's prose (`hardcoded_exit_code` doesn't distinguish code from
  plain text).

In other words, following the detector improvement below, this detector now
exhibits a pattern of being "fairly robust to misleading changes, and passes
ordinary legitimate changes cleanly" — but two other, unrelated known false
positives remain. With only 12 samples per subgroup, it is not yet known what
proportion of real-world commits this pattern would apply to in practice
(see Limitations).

Whether the LLM-based evaluation (`task.py` — wiring confirmed in CI, but
real-model results not yet run) can achieve a lower false-positive rate than
the baseline on the same 12 "misleading" samples (i.e., whether it can judge
by actual *meaning* rather than being fooled by surface appearance) is the
central question this evaluation task is meant to answer.

## Detector improvement (§DC, with a frozen-data procedure to avoid overfitting)

The two known limitations recorded in §DC ("can't tell a rename from a
deletion"; "mistakes a cosmetically-relocated skip line for a new one") were
addressed in 2026-11, following this procedure (decided and recorded before
starting):

1. First, **build and freeze ≥20 (24 used) new "misleading"-subgroup
   samples independently** (`evals/diff_audit/build_frozen_holdout.py`
   generates `data/frozen_rename_skipmove_holdout.jsonl`: 12 renames, 12
   cosmetic skip-line relocations). The existing 24 clean samples in
   `eval.jsonl` are not used to evaluate the improvement (their content has
   already been seen by this session during label crosscheck) — they are
   used only for regression checking.
2. Measure the frozen data with the **pre-fix** detector first (and record
   the number).
3. Only then modify the detector.
4. Measure the same frozen data again **after** the fix. Any regression is
   reported, not hidden.
5. Confirm on the existing "normal" subgroup (12 legitimate changes) that
   the fix did not introduce new false positives there.

Provenance of the frozen data: all 24 samples are newly authored synthetic
diffs. The 12 renames vary the function name only, keeping the body (1–5
lines, with variations like docstrings, multiple local variables, and
`pytest.raises`) completely unchanged. The 12 skip-line relocations
reproduce 12 different kinds of "cosmetic-only change" to an existing skip
marker: trailing comment addition, quote-style change, multi-line
reformatting, extra whitespace inside parentheses, an inserted blank line,
and reordering within a class body. None overlap with the existing 24
samples in `eval.jsonl`.

**Results on the frozen data** (reproducible with `python3
evals/diff_audit/measure_frozen_holdout.py`; details in
`data/frozen_holdout_results.json`):

| Subgroup | Before (round 1) | After (round 1) | After (round 2, below) |
|---|---|---|---|
| Overall (24) | 21/24 = 0.875 [0.690, 0.957] | 3/24 = 0.125 [0.043, 0.310] | **2/24 = 0.083 [0.023, 0.258]** |
| Rename (12) | 12/12 = 1.000 [0.758, 1.000] | 0/12 = 0.000 [0.000, 0.242] | 0/12 = 0.000 [0.000, 0.242] |
| Skip-move (12) | 9/12 = 0.750 [0.468, 0.911] | 3/12 = 0.250 [0.089, 0.532] | **2/12 = 0.167 [0.047, 0.448]** |

**The fix (round 1)**:
- `detect_test_deletion`: compares a removed function's body against the
  body of any added function with a new name, and treats it as a rename
  (excluded from "deletion") **only when the bodies match exactly**. If the
  body differs by even one character, it is conservatively still flagged as
  a deletion (never biased toward false negatives).
- `detect_skip_addition`: narrows the comparison to lines that contain a
  skip marker, and normalizes by stripping trailing comments, unifying
  quote style, and removing extra whitespace just inside parentheses before
  comparing.

**Regressions (round 1): none.** The existing "normal" subgroup (12 samples)
stayed at 0/12 before and after (no new false positives on legitimate
changes). Recall on all five existing shortcut categories is identical
before and after (1.000 stayed 1.000, 0.842 stayed 0.842) — the
false-positive reduction did not come at the cost of true-positive
detection.

**Round 2 fix (2026-11, following a further-improvements request)**: after
round 1, 3 of 12 skip-move cases still remained false positives. Looking
closer, these turned out to have two separate causes:

1. **Multi-line-reformatted decorator calls were not yet handled**
   (part of the `multiline_split`/`multiline_and_comment` tags): a
   single-line `@pytest.mark.skip(reason="...")` reformatted across
   multiple lines with unchanged content. Fixed by adding
   `_join_continued_statements()` to `parrhesia/diff_fraud.py` (a helper
   that merges a line whose parentheses are not yet balanced with the
   following lines, until they are, producing one logical line) and
   applying it before comparison in `detect_skip_addition`.
2. **The `skipif_reformat`-tagged frozen sample itself had a bug in the
   generator script**: the relevant case in `build_frozen_holdout.py`
   passed several physical lines as a single string with an embedded
   `\n`, so `_skip_move_sample()`'s `f"+{ln}\n"` prefixing only tagged the
   first line with `+`, silently dropping part of the diff (meaning this
   sample never actually exercised the intended "multi-line reformat"
   scenario at all). **The already-committed frozen file itself
   (`data/frozen_rename_skipmove_holdout.jsonl`) was left untouched**, per
   the anti-overfitting procedure above. Instead: (a) the generator
   script's case was fixed to use proper separate list elements, (b) a
   `ValueError` guard was added to `_skip_move_sample()` to catch this
   same mistake (an embedded newline in one element) if it recurs, and
   (c) this is documented here, in `DEFECTS.md`, and in the relevant
   source docstrings.

**Regressions (round 2): none.** The existing "normal" subgroup and recall
on all five categories are unchanged from round 1 (re-confirmed against
`eval.jsonl`).

**Remaining known limitation (the `multiline_and_comment` case)**: after
the round-2 fix, 1 skip-move case (part of the `multiline_and_comment` tag)
is still an unfixed false positive. This is because the trailing-comment
stripping regex (`_TRAILING_COMMENT_RE = re.compile(r"#.*$")`) is applied
to the already-joined multi-line string, so an inline `#` comment on a
continuation line eats everything after it — including a syntactically
necessary closing parenthesis that originally lived on a later physical
line — producing a normalization mismatch. This is locked in as a
regression by `tests/test_parrhesia_diff_fraud.py::
test_detect_skip_addition_known_limitation_comment_on_continuation_line`
(note: this limitation is conservative — it causes continued detection,
not a false negative).

## Limitations (as required by the brief)

- **The dataset's author and the tool's author are the same person**, and
  neither has received independent review. The label crosscheck (above) does
  not fully resolve this (see the circularity issue below as well).
- **Mostly synthetic diffs** (148 of 155, 95%), so the distribution does not
  represent real-world diffs. Real commits, given this repository's own
  nature, contained almost no real examples of shortcuts, so they were
  deliberately used only as clean contrast cases.
- **Building the detector and the labels with the same person and the same
  rules can cause circularity**: the synthetic samples for the five shortcut
  categories were built by explicitly implementing the very concepts the
  detector is meant to catch, so the labels were not decided independently of
  the detector's own regular expressions. The label crosscheck (above)
  confirms "does the detector behave as the labels say" — it does not resolve
  this circularity. In fact, finding two real detector defects (§DB) during
  the crosscheck process is itself evidence that this circularity is not
  total (there is real room for the detector's behavior and the label's
  intent to diverge).
- **Small sample size** means wide confidence intervals (12 samples per
  subgroup; after the fix, the Wilson 95% CIs are [0.047, 0.448] for the
  "misleading" subgroup and [0.000, 0.242] for the "normal" subgroup —
  roughly ±0.2 to ±0.4 points wide).
- **The frozen holdout data (24 samples) used to evaluate the detector
  improvement was also authored by this same session**, so it is not
  independent third-party verification either (the same "dataset author and
  tool author are the same person" limitation above applies here too). The
  frozen-data generator script itself also turned out to have a bug, from
  embedding multi-line content inside a single string (the frozen file
  itself was left unmodified; only the generator and its guard were fixed —
  see §DC). A narrower unfixed limitation also remains: decorators that are
  both reformatted across multiple lines and carry an inline comment
  (see §DC).
- **LLM evaluation results (actual numbers from a real model) have not been
  run** (see above), so as of this README, only the rule-based detector's
  baseline results can be reported. That `task.py` itself actually runs in
  CI (the mock-provider wiring check) has been confirmed, but this only
  confirms "the code runs" — it is still unknown "how accurate an LLM
  actually is at this task."

## Bugs found while developing this evaluation task

While cross-checking dataset labels, a recall bug was found and fixed in
`parrhesia/diff_fraud.py`'s `detect_exception_swallowing`, which uniformly
missed exception-swallowing via a specific exception type (e.g. `ValueError`).
A separate limitation was also found in `detect_exit_code_hardcoding`, which
cannot recognize `sys.exit(...)` calls whose argument is itself a nested
function call; this one was left as a documented, unfixed known limitation,
since verifying a safe fix needs more time (both are recorded in
`DEFECTS.md`'s `§DB`). Separately, the false positives on renames and
cosmetic skip-line relocations found via the clean false-positive-rate
measurement (above) were also fixed in 2026-11, following the
frozen-data before/after procedure described in "Detector improvement"
above (`§DC`).
