# evals/diff_audit — Inspect差分監査評価

Parrhesiaの検出対象である「AIエージェントが書いたコード差分に潜む5種類
のズル」を題材にした、[Inspect](https://inspect.ai-safety-institute.org.uk/)
(`inspect_ai`)ベースの評価タスク一式。

## 目的

Parrhesiaには、`git diff`から5種類のズル(テスト削除・スキップ追加・
アサーション弱体化・例外握り潰し・終了コード決め打ち)を機械的に検知する
ルールベース検出器(`parrhesia/diff_fraud.py`)が既にある。本ディレクトリ
は、

1. 同じ判定を**LLM自身にやらせた場合**にどれだけ正確か(Inspectタスク、
   `task.py`)
2. 既存の**ルールベース検出器そのもの**を同じデータで動かした場合の
   性能(ベースライン、`baseline.py`)

の両方を、同一のデータセット(`build_dataset.py`が生成)で測り、特に
「正当な変更をズルと誤判定してしまう率(誤検知率)」を信頼区間つきで
正直に報告することを目的とする。

## ファイル構成

```
evals/diff_audit/
  build_dataset.py   # データセット生成(標準ライブラリのみ、常に実行可)
  baseline.py         # ルールベース検出器によるベースライン評価(同上)
  task.py             # Inspectタスク本体(inspect_aiが必要)
  data/
    tune.jsonl              # 試行錯誤用(最終指標には使わない)
    eval.jsonl               # 最終評価用
    label_crosscheck.json    # ラベルの検算結果
    dataset_summary.json     # カテゴリ別・由来別の件数集計
    baseline_results.json    # ベースラインの実行結果・指標
  README.md           # 本ファイル
```

## 再現コマンド

### 1. データセットの生成(ネットワーク不要、常に実行できる)

```bash
python3 evals/diff_audit/build_dataset.py
```

### 2. ベースライン(ルールベース検出器)の評価(ネットワーク不要、常に実行できる)

```bash
python3 evals/diff_audit/baseline.py

pip install ".[evals]"

```

### 生成元についての正直な注記(依頼書への回答)

依頼書は「生成元は、リポジトリ内のテスト用データと実コミットを優先」
としていたが、実際にこのリポジトリの全コミット履歴(401件)を
`parrhesia.diff_fraud.analyze_diff()`で機械的にスキャンしたところ、
**5種類のズルを実際に行った実コミットはほぼ見つからなかった**(この
プロジェクトの性質上、意図的な手抜きコミットが少ないため)。見つかった
実コミットの大半は、むしろ「一見ズルに見えるが実際にはclean」という、
検出器の誤検知を誘発する側の実例(関数のリネーム・新規防御コードの
追加等)だった。

そのため本データセットは、**5つのズルカテゴリの陽性サンプルは
synthetic(全148件)**、**cleanの一部(7件)は実コミットから採取**、
という構成になっている。この比率の偏りは、合成データに偏っている
ことの限界として下記に明記する。採取した7件の実コミットは、全て
このセッション自身が2026-11-16に行った命名中立化コミット
(`ed829b5`・`fd17d6d`・`544ae37`)からの抜粋であり、中身をセッション
自身が直接把握しているため、ラベルの確実性が高い。

## ラベルの検算(依頼書の要求事項)

全155サンプルに対し、Parrhesia自身の検出器(`analyze_diff`)を適用し、
意図したラベルと機械的に照合した(`build_dataset.py`の
`crosscheck_labels()`、`data/label_crosscheck.json`)。

- 不一致: 23件
  - **既知の誤検知として意図的に設計した対照例**: 19件(関数のリネーム
    6件、skip行の見た目だけの移動6件、実コミット由来7件 — いずれも
    「検出器がどう誤検知するか」を示すためにわざと作った/選んだclean
    サンプル)
  - **既知のrecall限界**(後述の§DBで発見・一部修正): 4件
  - **分類不能な、未知の不一致**: **0件**

未知の不一致が0件であることは、`tests/test_evals_diff_audit.py::
test_label_crosscheck_has_no_unexpected_mismatches`で回帰的に固定して
いる。

**ラベルを検出器に合わせて変更した件数: 0件。** `crosscheck_labels()`
は意図した`category`ラベルを一切書き換えない、読み取り専用の照合関数
である(`build_dataset.py`のソースで確認できる)。各サンプルの
`category`は、生成テンプレートの時点(検出器の出力を見る前)で、
「そのdiffが実際に表す変更が何か」という視点のみで決めている
(例: リネームは、検出器がどう判定するかに関わらず、内容が変わって
いない以上`clean`である)。その後の検算で見つかった23件の不一致は、
全て「検出器側の挙動」側を記録・分類したのであり(意図的な対照例19件、
既知のrecall限界4件)、`category`ラベル自体を書き換えた箇所はどこにも
無い。ただし、下記の限界に記す通り、5つのズルカテゴリの陽性サンプル
自体を検出器が検知すべき概念を明示的に実装して作った(＝ラベルと検出器
が同じ人の同じ理解から出発している)という、より根本的な循環は残って
いる。

### [最重要指標] cleanの誤検知率(群ごとに別々に報告する)

eval.jsonl内のclean 24件は、狙いの異なる2群に分けて作っている。
「紛らわしい」群12件は、意図的に検出器の盲点を突く対照例として設計
した(関数のリネーム3件・skip行の見た目だけの移動3件・このセッション
自身の過去コミット6件からの抜粋)。「通常」群12件は、ごく普通の
正当な変更(テストの純粋な強化4件・意味が同じ等価なリファクタ4件・
`except ... as exc: raise`のような正しい例外処理4件)である。

**[2026-11、外部レビューの指摘を受けて変更] この2群を合算した単一の
誤検知率(旧版は「50%」と見出しに書いていた)は、著者がこの2群を
概ね半々に構成したことで決まる、混合比率依存の数字であり、検出器
そのものの性能指標としては意味が薄いため、見出しからは外す。** 代わりに、
`python3 evals/diff_audit/baseline.py`(`baseline.py`内の`wilson_ci()`、
手計算ではなくコードで算出)で実測した、群ごとの誤検知率を報告する:

| 群 | 件数 | 誤検知された件数 | 誤検知率 | Wilson 95%CI |
|---|---|---|---|---|
| 紛らわしい(リネーム・skip移動・実コミット) | 12 | 12 | 1.000 | [0.758, 1.000] |
| 通常(強化・等価リファクタ・正しい例外処理) | 12 | 0 | 0.000 | [0.000, 0.242] |

(参考・見出しには使わない)2群を合算した場合: 12/24 = 0.500
(Wilson 95%CI: [0.314, 0.686])。この合算値は、本READMEの
`data/baseline_results.json`では
`clean_false_positive_rate_combined_rate_mixture_dependent_do_not_use_as_headline`
というキー名で、そのまま「見出しに使うな」という注意書きつきで記録
している。

**「通常」群0/12件という結果についての注意**: このデータセットは
検出器の作者自身が作っており、「通常の変更なら検出器は誤検知しない
だろう」という予想に沿うデータを無意識に選んでしまう(＝検出器に
都合の良いデータだけを「通常」に分類してしまう)楽観バイアスが
かかり得る。0/12という数字は、独立した第三者が作った「通常」の
変更セットでも同じく成り立つかどうかまでは保証しない。

(補助指標、単独では主張に使わない)全体正解率: 0.853

**誤検知の主な原因**(内訳の中身で確認済み):
- リネーム3件は全て`deleted_test`として誤検知された(`detect_test_
  deletion`が「削除された関数名が、追加側に同名で存在するか」しか
  見ておらず、別名へのリネームを区別できないため)。
- skip行の見た目の移動3件は全て`skip_marker`として誤検知された
  (`detect_skip_addition`が、削除側の行と文字列として完全一致しない
  限り「新規追加」とみなすため、インデントやコメントが変わっただけ
  でも誤検知する)。
- 実コミット6件も同じ2つの原因(リネーム4件、新規ファイル1件への
  except/pass新設、Markdown地の文中の文字列一致1件)で誤検知された。

つまりこの検出器は、「紛らわしい変更には弱いが、普通の正当な変更は
きちんと通す」という、単純な「誤検知率が高い/低い」では捉えきれない
傾向を持つ。この傾向自体は実測で確認できたが、各群12件という標本数
では、この傾向が実運用でのコミット全体に対してどの程度の比率で
現れるかまでは分からない(限界セクション参照)。

LLMベースの評価(`task.py`。配線はCIで確認済みだが、実モデルでの結果は
未実行)が、同じ「紛らわしい」群12件に対してベースラインより低い誤検知率
を達成できるか(=表面上の見た目に惑わされず「意味」を理解して判定できる
か)が、本評価タスクの核心的な問いである。

## 限界(依頼書が要求する項目)

- **データセットの作成者とツールの作成者が同一**であり、独立した検証を
  受けていない。ラベルの検算(上記)はこの欠陥を完全には解消しない
  (下記の循環の問題も参照)。
- **合成差分が多い**(155件中148件、95%)ため、実世界の差分の分布を
  代表しない。実コミットは、このリポジトリ自身の性質上、ズルの実例を
  ほとんど含んでいなかったため、意図的にcleanの対照例としてのみ採用
  した。
- **検出器とラベルを同じ人・同じ規則で作ると、循環が起こりうる**:
  5つのズルカテゴリの合成サンプルは、検出器が検知すべき概念(テスト削除
  ・skip追加等)そのものを明示的に実装して作ったため、検出器の正規表現
  と独立にラベルを決めたわけではない。ラベルの検算(上記)は「検出器が
  ラベル通りに動くか」を確認するものであり、この循環を解消するものでは
  ない。実際、検算の過程で検出器側の欠陥(§DB)を2件発見できたことは、
  この循環が完全ではない(検出器の挙動とラベルの意図がズレる余地が
  実際にある)ことの証拠でもある。
- **標本数が小さい**ため、信頼区間は広い(各群12件、Wilson 95%CIは
  「紛らわしい」群が[0.758, 1.000]、「通常」群が[0.000, 0.242]と、
  どちらも±0.24ポイント程度の幅がある)。
- **LLMでの評価結果(実モデルでの数字)は未実行**(上記参照)であり、
  本READMEの時点で報告できるのはルールベース検出器のベースライン結果
  のみである。`task.py`自体がCIで実際に動くこと(モックプロバイダでの
  配線確認)は確認済みだが、これは「コードが動く」ことの確認であり、
  「LLMがこのタスクで実際にどれだけ正確か」はまだ分かっていない。

## 本評価タスクの開発過程で見つけた不具合

データセットのラベル検算の過程で、`parrhesia/diff_fraud.py`の
`detect_exception_swallowing`が、個別の例外型(`ValueError`等)による
握り潰しを一律で見逃すrecall上の欠陥を発見し、修正した。
`detect_exit_code_hardcoding`にも、ネストした関数呼び出しを引数に取る
`sys.exit(...)`を認識できない別の限界を発見したが、こちらは安全な修正
方法の検証に追加の時間が必要なため、未修正の既知の限界として記録に留めた
(両方とも`DEFECTS.md`の`§DB`に記録済み)。
